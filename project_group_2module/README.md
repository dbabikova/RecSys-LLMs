## Общий протокол: что известно, а что pending

Уже задано: FAR-Trans; ранжированный **Top-10 активов для каждого оцениваемого
пользователя**; основная метрика **nDCG@10 по будущим покупкам**.
Для всех команд общие пользователи, eligible universe, временной сплит и правила
исключений. Во внутреннем сравнении также одинаковая информация на входе.
Промежуточные кандидаты разных методов не обязаны совпадать; фиксировать один
набор можно, чтобы изолировать реранкинг.

Ниже — предварительные допущения для будущего проектирования, **не официальный
протокол и не выводы из данных**. Преподаватель утвердит общий протокол до Session 2.

| Параметр | Что ещё не утверждено | Рабочее допущение / что делаем до утверждения |
|---|---|---|
| Временной срез и окна | Официальная дата cut, границы train / validation / test, горизонт будущих покупок | Для EDA вычислен последний допустимый шестимесячный срез по ценовому покрытию статьи: даты и граничные правила генерируются в `reports/split.md`. Это не официальный протокол; настройка будущих моделей должна быть до теста |
| Оцениваемые пользователи | Общий список и критерии включения, минимальная история, cold-start и пользователи без положительных меток | Для диагностик по статье нужны прошлый Buy в eligible universe и будущая релевантная пара; cold-start до фильтра посчитан отдельно. Для официальной оценки правило требует подтверждения |
| Набор активов | Общий eligible universe, допустимые типы, доступность актива к cut и исключения | Не ограничиваем план только акциями: FAR-Trans содержит акции, фонды и облигации. Предварительно рассматриваем все три типа при подтверждённой доступности к cut; конкретный перечень и фильтры пока не задаём |
| Разметка транзакций | Точная трактовка Buy / Sell, повторных покупок и уже известных пар; обработка реконструированных событий и дубликатов | Для EDA посчитаны A (новые пары) и B (все Buy-пары), обе с бинарной релевантностью; отрицательные ID исключены из меток. Реконструкции в train сохраняются только для диагностики подхода статьи; отдельно посчитана чувствительность без них. Официальный выбор не сделан |

Эти допущения нельзя выдавать за замороженный benchmark. После утверждения
заменяем их официальными правилами и фиксируем изменение в `DECISIONS.md`.
До этого любые будущие локальные проверки помечаем provisional.

Дополнительно пока не известны правила учёта preprocessing/cache при официальном
тайминге, состав сравнительных когорт и окончательные критерии валидной финальной
сдачи. Их не придумываем. В плане предлагаем раздельно измерять обучение и
end-to-end генерацию рекомендаций, явно указывая оборудование и кеширование.

## Требования к будущему плану эксперимента

- Классический baseline и non-LLM контроль получают ту же доступную информацию,
  что и LLM; иначе эффект данных смешивается с эффектом метода.
- Абляция изолирует LLM-компонент; для Hybrid отдельно разделяем Encoder и Ranker.
- Фиксируем модель/версию, способ построения контекста и бюджет. Для стохастического
  плана описываем повторы и вариативность; для реранкера — чувствительность к
  порядку кандидатов и валидацию выдаваемых ID.
- Измеряем nDCG@10, runtime и стоимость. LLM judge не является единственной
  истиной; объяснения и самосгенерированные scores не доказывают точность.
- Учитываем приватность, этику, временные утечки и contamination предобучения.
  Не отправляем сырые клиентские данные внешнему API без отдельного решения.
- Положительный, отрицательный и нулевой результаты допустимы.
  Предсказание покупки не доказывает прибыльность или инвестиционную пригодность.
  Не заявляем причинный эффект на доходность или принятие пользователем.
- В §4 не выдумываем числа: до запуска описываем только planned evaluation.
  Новизну формулируем как «не нашли исследование X при условии Y», а не «работ нет».

## Воспроизведение этапа изучения данных

Из этой папки при установленном Python и зависимостях:

```powershell
python -m pip install -r scripts/requirements.txt
python scripts/run_analysis.py --archive "C:\Users\User\Downloads\FAR-Trans.zip"
```

После первого копирования архива достаточно одной команды:

```powershell
python scripts/run_analysis.py
```

В текущем окружении `python` из PATH — Windows Store stub. Проверенный запуск:

```powershell
& "C:\Users\User\anaconda3\python.exe" scripts/run_analysis.py
```

Корень проекта определяется относительно файла скрипта, не cwd. Чужие папки не
читаются как входы анализа и не изменяются. Скрипт не перезаписывает отличающийся
архив или извлечённый файл. Все графики строятся из CSV, синтетические данные
используются только в тестах. Пайплайн автоматически запускает self-tests,
независимую stdlib-проверку ориентиров и проверку отсутствия customerID в отчётах.
Версии среды, хеши исходников, сырых файлов и результатов зафиксированы в
генерируемых `source.md`, `summary.json` и `manifest.json`.
Для той же среды повторный запуск должен давать побайтово одинаковые артефакты.

Проверенные первичные результаты — [reports/eda.md](reports/eda.md), схема —
[reports/schema.md](reports/schema.md), утечки — [reports/leakage.md](reports/leakage.md),
границы предварительного протокола — [reports/split.md](reports/split.md).
Текущие ориентиры не объявляются leak-free из-за реконструкций в train и
ограничений provenance релиза.

Содержимое `data/`, кроме пустого `.gitkeep`, исключено из Git.
Полный экспорт AI-сессии проверяем на секреты и приватные данные перед сдачей;
публикация экспорта на GitHub не является частью текущего шага.
