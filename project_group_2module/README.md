## Протокол: подтверждённое правило повторов и настройки HW2

Уже задано: FAR-Trans; ранжированный **Top-10 активов для каждого оцениваемого
пользователя**; основная метрика **nDCG@10 по будущим покупкам**.
Для всех команд общие пользователи, eligible universe, временной сплит и правила
исключений. Во внутреннем сравнении также одинаковая информация на входе.
Промежуточные кандидаты разных методов не обязаны совпадать; фиксировать один
набор можно, чтобы изолировать реранкинг.

**Новое подтверждение преподавателя:** previously purchased assets may be
recommended; project includes both repeat and new purchases; keep the starter's
default repeat-allowed setting and compare against all four provided baselines.
Повторы **разрешены и релевантны**, это больше не pending.

Официальный исходный код и инструкции — `dryjins/RecSys-LLMs`, `project/far-trans`.
Они прочитаны в отдельном клоне `../../course-starter`, вне репозитория Дарьи.
Commit, хеши исходников, protocol_hash и измеренное время записываются скриптом
в `reports/starter_baselines.md` / `reports/starter_summary.json`.

| Параметр | Подтверждено сейчас | Граница применимости |
|---|---|---|
| Разметка | Будущие Buy дают binary distinct user–asset relevance, включая уже купленные assets; `exclude_seen=False` | Правило повторов подтверждено для проекта; A (new-only) в `split.md` остаётся только исторической диагностикой, не альтернативой официальной постановке |
| Время HW2 | Cut `2021-06-01`; history строго раньше; labels `[2021-06-01, 2021-07-01)` — 30 дней | Это обязательные teaching defaults HW2, не финальный grading test проекта |
| Пользователи HW2 | Детерминированная выборка 100 as-of-known warm users самого starter; zero truth не удаляется | Полный warm запуск `--max-users 0` — дополнительная диагностика. Не путать с `--cohort all` |
| Universe starter | Есть metadata строго до cut и хотя бы одна положительная цена строго до cut | Все типы активов, не stocks-only; не требуется полное будущее покрытие ценами. Финальный тестовый universe не объявлен этим demo |
| Очистка starter | Negative transactionID исключены из history и truth; удаляются только точные полные duplicate rows | Остальные provenance-риски из `leakage.md` не считаются автоматически устранёнными |
| Метрика HW2 | Primary nDCG@10 по всем выбранным users с empty truth = 0; отдельно nonempty mean и число users | Нельзя заменить primary более высокой nonempty средней |
| Baselines | Popularity, CBF, Latest buy, Latest buy or sell — все четыре обязательны, используются реализации starter | Старые Popularity / Repeat+Popularity из EDA имеют другие правила и не подменяют их |

Прежний шестимесячный EDA-сплит в `split.md` сохранён для диагностики:
ни его cut, ни полный ценовой фильтр, ни сохранение реконструкций в истории
не являются настройками HW2. Его B совпадает с проектом по принципу разрешения
повторов, но не по остальным правилам. Финальные даты, пользователи и universe
итогового проекта не считаются замороженными учебными defaults.

Дополнительно пока не известны правила учёта preprocessing/cache при официальном
тайминге, состав сравнительных когорт и окончательные критерии валидной финальной
сдачи. Их не придумываем. В плане предлагаем раздельно измерять обучение и
end-to-end генерацию рекомендаций, явно указывая оборудование и кеширование.

## Требования к будущему плану эксперимента

- Классический baseline и non-LLM контроль получают ту же доступную информацию,
  что и LLM; иначе эффект данных смешивается с эффектом метода.
- Абляция изолирует LLM-компонент; для Hybrid отдельно разделяем Encoder и Ranker.
- HW2 требует публичную open-weight модель и runnable код реального инференса;
  identity extension, экспорт prompts и post-hoc oracle не выполняют это требование.
- Фиксируем модель/версию, способ построения контекста и бюджет. Для стохастического
  плана описываем повторы и вариативность; для реранкера — чувствительность к
  порядку кандидатов и валидацию выдаваемых ID.
- Измеряем nDCG@10, runtime и стоимость. LLM judge не является единственной
  истиной; объяснения и самосгенерированные scores не доказывают точность.
- Учитываем приватность, этику, временные утечки и contamination предобучения.
  Не отправляем сырые клиентские данные внешнему API без отдельного решения.
- Положительный, отрицательный и нулевой результаты допустимы.
  Предсказание покупки не доказывает прибыльность или инвестиционную пригодность.
  Не заявляем причинный эффект на доходность или принятие пользователем.
- В §4 не выдумываем числа: до запуска описываем только planned evaluation.
  Новизну формулируем как «не нашли исследование X при условии Y», а не «работ нет».

## Воспроизведение этапа изучения данных

Из этой папки при установленном Python и зависимостях:

```powershell
python -m pip install -r scripts/requirements.txt
python scripts/run_analysis.py --archive "C:\Users\User\Downloads\FAR-Trans.zip"
```

После первого копирования архива достаточно одной команды:

```powershell
python scripts/run_analysis.py
```

В текущем окружении `python` из PATH — Windows Store stub. Проверенный запуск:

```powershell
& "C:\Users\User\anaconda3\python.exe" scripts/run_analysis.py
```

Корень проекта определяется относительно файла скрипта, не cwd. Чужие папки не
читаются как входы анализа и не изменяются. Скрипт не перезаписывает отличающийся
архив или извлечённый файл. Все графики строятся из CSV, синтетические данные
используются только в тестах. Пайплайн автоматически запускает self-tests,
независимую stdlib-проверку ориентиров и проверку отсутствия customerID в отчётах.
Версии среды, хеши исходников, сырых файлов и результатов зафиксированы в
генерируемых `source.md`, `summary.json` и `manifest.json`.
Для той же среды повторный запуск должен давать побайтово одинаковые артефакты.

## Пример под выбранный Ranker RQ, без запуска моделей

```powershell
& "C:\Users\User\anaconda3\python.exe" -B scripts/make_ranker_example.py
& "C:\Users\User\anaconda3\python.exe" -B scripts/verify_example.py
```

Генератор использует функции starter и сверяет demo с сохранённым CLI-запуском.
Verifier не импортирует starter или наши модули: сам читает сырые CSV,
пересчитывает cohort/selection, record, history, profile, metadata, CBF20,
Latest buy и nDCG. При расхождении завершает работу с ошибкой; точный checklist
и числа печатает в `reports/verify_example.md`. Тест `test_verify_example.py`
проверяет отказ при намеренно испорченном expected metric с последующим
восстановлением нашего приватного evidence.

Приватные expected/input/result JSON — только в игнорируемом
`data/ranker_example/`. Публичные отчёты маскируют все customerID.
Показанный CBF20 — иллюстрация размера RQ, не выбор финального pool.
Same-information input — черновой контракт: raw Buy dates показаны для аудита,
но пока не добавлены в stock history context ни для одного метода.
Ручная проверка в `verify_example.md` оставлена Дарье; её выполнение не заявляется.

Проверенные первичные результаты — [reports/eda.md](reports/eda.md), схема —
[reports/schema.md](reports/schema.md), утечки — [reports/leakage.md](reports/leakage.md),
границы предварительного протокола — [reports/split.md](reports/split.md).
Текущие ориентиры не объявляются leak-free из-за реконструкций в train и
ограничений provenance релиза.

Содержимое `data/`, кроме пустого `.gitkeep`, исключено из Git.
