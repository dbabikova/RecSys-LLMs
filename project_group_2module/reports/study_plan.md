# Minimal study plan — Session 1

**Автор:** Бабикова Дарья. **Трек:** Ranker. **Статус:** planned.
Модели не запускались, новых расчётов нет. Наблюдения ниже взяты только из готовых отчётов; лимиты и параметры — план, не измеренные результаты.

**RQ:** We test whether zero-shot LLM reranking of a fixed top-20 candidate list improves nDCG@10 over a classical learned reranker (LightGBM LambdaMART) that sees the same user and asset information and the same candidates, for the common FAR-Trans evaluation users.

## How Will You Test Your Question?

| Элемент | Запланированный эксперимент |
|---|---|
| **Data and users** | Протокол starter: history строго до **2021-06-01**, метки Buy в **[2021-06-01, 2021-07-01)**, 30 дней. Demo — **100** warm users, из них **11** с покупками; дополнительный full warm — **10 404**, из них **1 178** с покупками. Повторы **разрешены и релевантны по ответу преподавателя**; метки — distinct user–asset пары. Empty truth остаётся в primary nDCG с нулём. Eligibility: metadata и положительная цена строго до cut; negative transactionID исключены, удаляются только exact full duplicates. Это teaching split, не финальный test проекта. Поля и подгруппы — ниже. |
| **Method and baseline** | Обязательно сохраняем оригинальные **Popularity, CBF, Latest buy, Latest buy or sell**. Главный контроль — **LightGBM LambdaMART**, objective `lambdarank`, группа = user×cut, те же 20 кандидатов и поля. Обучение — на более ранних срезах, **окна меток заканчиваются строго до 2021-06-01**; отдельные ещё более ранние validation-окна для настройки. Вмешательство — zero-shot open-weight LLM, кандидат **Qwen3-8B**; точная revision фиксируется в Session 2. План: non-thinking, `temperature=0`, без few-shot и дообучения; локальный Transformers/vLLM inference. Ответ: десять уникальных candidate IDs в ranker-формате starter. |
| **Fair comparison** | Одинаковые пользователи, cut, eligible universe, truth, scorer и **фиксированный top-20 pool** у LLM и LambdaMART; этот pool нужен только для изоляции реранкинга. Четыре provided baseline сохраняют свой полный разрешённый universe, не обрезаются задним числом. Исходный порядок pool — дополнительный reference, не главный контроль: иначе эффект новых полей смешивается с эффектом метода. **Первый шаг Session 2 — выбрать и заморозить общий pool с ранее купленными активами пользователя до запуска моделей**, не выбирать его здесь. Правило состава/квот и отбора при истории длиннее 20 фиксируется на past-only development cuts, без вставки будущих Buy. |
| **Measure** | Primary — macro **nDCG@10 по всем** выбранным users; отдельно nonempty mean **с числом пользователей**. Сравниваем парную разность LLM−LambdaMART на тех же users, не только абсолютные значения. Измеряем latency на пользователя (среднее, медиана, p95), время полного прогона, preprocessing/model loading и обучение контроля отдельно; hardware, batch/cache policy одинаково документируются. Стоимость: GPU-часы и input/output tokens, включая все перестановки, повторы и invalid calls. Считаем malformed/out-of-pool/duplicate/неполные ответы и fallback users. Candidate recall/oracle — отдельная диагностика, не основная метрика. |
| **Contribution check** | Четыре заранее заданные абляции приведены ниже. Pool, пользователи и labels не меняются. При удалении информации те же поля убираются у LambdaMART и контроль переобучается на прошлых окнах. Сравниваем основной метод и его абляцию, а также их разность относительно соответствующего same-information контроля. |
| **Repeats and variance** | LLM: **3 фиксированные перестановки**, permutation seeds **17, 42, 2026**, состав pool неизменен. Основная выдача — агрегация трёх Top-10: баллы 10…1, отсутствующим ID — 0, tie-break ISIN; затем десять лучших из pool. Публикуем также каждую перестановку и разброс между ними. LambdaMART: **5 seeds — 0, 1, 2, 3, 4**, одинаковая настройка; если алгоритм детерминирован и результаты совпали, честно сообщаем нулевой разброс. Отдельно показываем распределение per-user nDCG и парных разностей, медиану/квантили, среднее и SD по повторам. Перестановки и seeds — не независимые новые пользователи. |
| **Risks / integrity** | Contamination: модель обучалась после 2021; даже локальный zero-shot не исключает знания будущего. Маскируем недоступные поля, проверяем анонимизацию активов, не считаем её доказательством полной чистоты. Сохраняем ограничения reconstructed events, back-adjusted prices/units, перенесённых дат, backdated metadata и late questionnaire из `leakage.md`. Приватность: локальный inference, **customerID не попадает в prompt**; aliases и обратное отображение — только в игнорируемом `data/`. LLM-судья **не используется**. nDCG измеряет совпадение с покупками, не suitability, доходность, принятие советов или причинный эффект. |
| **Feasibility** | Python, исходный starter/evaluator, LightGBM, Transformers или vLLM; source commit, CSV hashes, model repository/revision, prompts, dependencies, decoding и hardware фиксируются. Предварительный лимит — **до 8 GPU-часов и одного CPU-дня**, без платных model API; наличие локальной/облачной GPU проверяется в Session 2, ресурсы сейчас не заказываются. Demo и его абляции — обязательный первый объём, full warm — расширение после pilot latency. Если лимит не позволяет завершить весь cohort, сообщаем incomplete, не исключаем сложных users и не выдаём подвыборку за full warm. Шаги по сессиям — ниже. |
| **Interpretation** | **Положительный:** устойчивый положительный LLM−LambdaMART при том же pool/информации показывает пользу метода в данных условиях; отдельно проверяем цену и положение относительно четырёх baseline. **Нулевой:** нет убедительного прироста при данном дизайне/ресурсах; это не доказательство эквивалентности всех LLM. **Отрицательный:** LLM ухудшает ranking или не оправдывает стоимость; анализируем candidate ceiling, invalid outputs, bias и подгруппы, не скрываем результат. Ни один исход не доказывает инвестиционную пригодность или прибыль. |

## Общие входные поля и время доступности

Сохраняем контракт [ranker_example.md](ranker_example.md), §6; один payload для обоих методов, разные способы обработки.

| Поля | Статус и дата | Передача / защита |
|---|---|---|
| History: asset ID, name, categorical attributes, `buy_count`, metadata timestamp | Observed/derived из сохранённых Buy **< cut**; metadata **< cut**, но историчность имён не доказана | Одинаковая история и одинаковая заранее фиксированная truncation для LLM/контроля. **Дат Buy в stock context нет**; raw dates — audit-only, metadata timestamp не заменяет recency. |
| Candidate: ID, name/short name, category/subcategory, sector/industry, marketID, metadata timestamp; исходные score/rank | Observed/missing metadata **< cut**; score/rank derived только из прошлого | Один и тот же pool/поля. LambdaMART: categorical encoding, числовые aggregates/similarities и text TF-IDF признаки названий/истории, fitted только на training. Не заменять доступный LLM текст одними ID. |
| Profile: customerType, riskLevel, investmentCapacity, status/placeholder flags, snapshot timestamp | Последний snapshot **< cut**; `Predicted_*` = estimated, пусто/Not_Available = missing, остальные — observed labels, не гарантия provenance | `lastQuestionnaireDate` — availability audit. Анкета **≥ cut** → risk/capacity withheld обоим; sentinel/неподтверждённое время оценки не выдаются за наблюдённое предпочтение. Missing/estimated markers сохраняются. |
| Cutoff, user alias, candidate ID mapping | Параметр протокола / служебный ключ | Alias не является семантическим признаком; исходный customerID только для локального join/output, не в prompt. |
| Future Buy/ISIN/date и truth | Только labels в 30-дневном окне | Никогда не входят в признаки/промпт. Future Sell не является отрицательной меткой. `totalValue`, `units`, channel, future prices и full-period profitability не используются. Цена строго до cut нужна только для eligibility. |

**Подгруппы заданы заранее:** (а) repeat targets = актив покупался до cut, new targets = не покупался; условные denominators и количество users публикуются отдельно, один user может иметь оба типа; (б) длина **retained Buy-истории до cut**: 1–5, 6–20, >20 событий. Distinct assets показываем отдельно, не называем их числом сделок. Подгруппы не меняют cohort, модель или primary mean; будущая repeat/new разметка используется только при анализе, не для настройки.

## Абляции

| Изменение | Что изолирует / ограничение вывода |
|---|---|
| **Без названий активов** | У обоих методов убрать names/short names/тикеры, ISIN в model input заменить согласованными aliases, сохранив связи history↔candidate и разрешённый output mapping. Проверяет зависимость от узнавания эмитента/возможных поздних знаний; остаются косвенные подсказки в категориях, поэтому contamination полностью не исключается. |
| **Без истории** | Убрать явную историю, counts, history-derived similarities и исходные history-based scores/ranks из model inputs обоих методов. Изолирует добавочную пользу **явного** поведенческого контекста: фиксированный retriever pool всё ещё несёт исторический сигнал, это не “без истории во всей системе”. |
| **Без профиля** | Убрать customerType/risk/capacity и их profile markers у обоих методов. Изолирует вклад профиля, в том числе оценённых/ошибочных значений, без отбора пользователей по качеству профиля. |
| **Исходный порядок, без перестановок** | LLM получает исходный порядок pool в трёх вызовах, та же агрегация и бюджет, что у основного варианта. Сравнение изолирует чувствительность к presentation order при неизменном составе/полях; отдельный одиночный исходный вызов можно показать как latency reference, не смешивая его с equal-budget эффектом. |

## Фиксация протокола и ошибки

- Уже измерено на **full warm nonempty users**: oracle исходного CBF50 **0,4544**, Latest buy **0,4648** ([starter_baselines.md](starter_baselines.md)). Для вложенного CBF20 этот риск не слабее. Это не основание обещать победу и не выбранный здесь новый generator. Повторные assets должны участвовать в проектируемом pool; при более чем 20 собственных assets правило отбора будет past-only.
- До моделей в Session 2 фиксируем pool policy, источники/CSV hashes, cohort, preprocessing, prompt, revision, seeds, aggregation и invalid policy. Новый top-20 protocol/policy hash **не подменяем** сохранённым default CBF50 hash. Настройки выбираем на ранних development cuts; уже просмотренное июньское teaching-окно не считаем нетронутым holdout. Финальный общий тест — по будущему протоколу преподавателя, без настройки по его результатам.
- Ranker response file: `user_id`, `stage="ranker"`, `protocol_hash`, `ranked_ids`; в prompt — alias, не исходный user_id. Adapter валидирует ровно десять уникальных ID из общего pool. **Invalid → исходный Top-10 того же pool**, флаг ошибки и учёт времени/токенов; user остаётся в метрике. Не подменять fallback полной CBF-выдачей вне pool. После adapter ответы проходят проверки starter; неожиданный сбой останавливает прогон для исправления, не удаляет строки.
- Для main и каждой абляции храним raw responses локально, результаты по каждому user, все повторы и flags. Замороженные настройки не подбираем по иллюстративному пользователю. Ручная проверка Дарьи из `ranker_example.md` ещё не заявляется выполненной.
